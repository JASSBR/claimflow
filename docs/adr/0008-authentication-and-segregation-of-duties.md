# 0008 — Authentication, roles and segregation of duties

- **Status:** Accepted · 2026-10-02

## Context

Claims handling is a regulated activity: who decided what must be traceable, nobody should approve unlimited amounts
alone, and the person approving a payment must not be the one releasing it. At the same time, a public demo must let
a recruiter log in within one click — no account creation, no password.

## Decision

**Authentication — one validation pipeline, two key sources.** The API is an OAuth 2.0 resource server validating
JWT bearer tokens with standard OIDC claims (`sub`, `name`, `role`; `MapInboundClaims = false`).

| `Auth:Mode` | Who issues tokens | Validation key |
|---|---|---|
| `Oidc` (default) | Entra ID, Keycloak, any OIDC provider | provider JWKS via `Authority` |
| `Demo` | built-in `/api/auth/token` endpoint, 4 personas | HMAC key from a secret store |

The demo provider is ~80 lines, only mapped in `Demo` mode, and its key is generated by Aspire (local) or stored as a
platform secret (Azure). Options are validated at startup: a misconfigured API refuses to boot. SignalR receives the
token through `access_token` (browsers cannot set headers on WebSockets), accepted only on `/hubs`.

**Authorization — two layers, one answer.**

- *Who may attempt an action* is role-based and lives in the module (`ClaimPermissions`, policies `claims.read` /
  `claims.write` registered by the module itself): handlers and managers work files, only managers release payments,
  auditors read.
- *Whether the action is legal on this claim* is a **domain rule**:
  - **Delegated authority** ("délégation de pouvoir"): `Approve` receives an `ApprovalAuthority(approver, limit)`;
    a handler's limit is configuration (`Claims:HandlerApprovalLimit`, 10 000 € by default), above it → 403
    `claim.approval_limit_exceeded`.
  - **Four-eyes principle**: `Settle` by the approver → 403 `claim.four_eyes_violation`.
  - **Audit trail**: every transition records its actor; events carry the actor's name to the realtime feed.
- The API returns `allowedActions` = workflow ∩ role ∩ segregation of duties, computed **for the caller**. The UI renders
  exactly that list, so Karim never sees "Release payment" on a claim he approved himself.

## Consequences

- ✅ Swapping the demo provider for Entra ID is configuration only (`Auth:Mode=Oidc`, `Auth:Authority=…`).
- ✅ Segregation of duties is unit-tested in the domain and integration-tested end to end (`SecurityTests`), including a
  forged token and anonymous access to the hub.
- ⚠️ The demo provider issues tokens to anyone who asks — acceptable for seeded demo data, never for real data;
  it is disabled unless `Auth:Mode=Demo` is set explicitly.
